## Collect geometric neighbors per agent type without redundant copies

- [ ] Refactor the optional local collection helpers in `src/GeometricMethods.jl` to collect one batch per registered neighbor type. Check the `:Immortal` hint once per type and dispatch to a dedicated helper. The mortal helper keeps the `read.died` check; the immortal helper never reads the death flags. Both apply `neighbor_filter` if present and keep positions, IDs, and projections aligned. Leave merging and replication to the backend; do not add a `borrow_identity` flag.
- [ ] For an unfiltered `:Immortal` batch, every slot contributes one entry. Evaluate `posfunc` once per state and generate the IDs with `collect(base_id .+ (1:length(states)))`, where `base_id = agent_id(typeid(sim, agent_type), AgentNr(0))`. Do not add a separate slot-limit check here. With `project === identity` and a matching registered projection type, return `read.state` itself as the projection vector, not a copy. For filtered batches, retain only the matching slots; for other projections, compute the registered projection values.
- [ ] In `ReplicatedKDTree`, keep IDs and projections segmented by neighbor type rather than appending them into global flat vectors. Only the positions used to build the shared KD-tree index need a common ordering. Record the segment boundaries so a tree hit maps to a batch and local index (for example, if batch A contains 100 entries, hit 107 is entry 7 of batch B). Use that mapping for self-exclusion and for the ID, projection, and pair accessors. The pair accessor should resolve the batch and local index once. Do not run another spatial query. For a single type, avoid unnecessary merging or segment lookup.
- [ ] Preserve snapshot ownership. MPI `join` already creates an owned replicated vector, so an eligible `read.state` can go straight into `join`; keep its result without copying it again into a flattened projection array. In serial execution, keep a borrowed buffer only when it cannot change before the queries finish. In particular, a neighbor type with `:Independent` can update its read storage in place, so copy when necessary to preserve the snapshot. Never mutate a borrowed buffer.
- [ ] Verify the layout against the backend-neutral spatial tests and add coverage for multiple neighbor types, filtered and unfiltered paths, identity and non-identity projections, self-exclusion across segment boundaries, empty local batches, and snapshot behavior under `:Independent`. Measure end-to-end `geom_prepare!` time and allocations in serial and MPI, and check the cost of mapping hit indices during queries. Per-type joins may increase the number of collectives relative to the current combined join; measure this trade-off rather than assuming a net win.

**Background.** The old `ConnectSpatial.jl` collected and joined one type at a time. Its `_get_ids_poss_states` wrapper appended the per-type results when several types were requested (and appended the projection data only when an edge constructor was present). The current collector flattens the local data before `join`. Moving that flattening after `join` would only move the projection copy; keeping the per-type vectors is what avoids it.

**Local benchmark, not yet implemented.** With 600,000 agents of one immortal type, no filter, and identity projection (Julia 1.12.6 on aarch64, median of 17 warmed runs excluding reported GC time), the current collector took 1.81 ms / 18.31 MiB for 16-byte states and 3.06 ms / 45.78 MiB for 64-byte states. Returning `read.state` directly with one `agent_id` call per slot took 1.23 ms and 1.42 ms, respectively, at 9.16 MiB in both cases. Returning `read.state` and generating IDs from a base ID plus the slot range took 0.19 ms and 0.40 ms at the same 9.16 MiB. The variants produced the same results; MPI, tree construction, and query costs were not measured.
